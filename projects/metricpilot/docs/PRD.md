# MetricPilot 产品需求文档 · MVP v1

状态：已实现个人演示 MVP；未开展真实用户访谈或上线验证。本文区分产品假设、实现事实和后续验证计划。

## 问题、用户与价值

待验证的问题假设：中小 SaaS 运营人员在查看营收、渠道和退款情况时，可能因为指标分母不一致、临时查询依赖分析师、AI 数字缺乏来源而反复核对。现阶段没有调研样本证明这些问题发生的频次或损失。

假设用户画像 A：运营专员，熟悉业务但 SQL 能力有限，需要快速比较渠道净收入并给同事发送可复核的说明。画像 B：产品经理，需要检查版本/套餐退款情况，避免用订单占比解释金额退款损失。画像 C：数据分析师，需要确认 AI 用了哪张表、哪段时间、哪个查询，判断答案能否进入周报。这些是设计用画像，不是访谈统计结果。

产品价值主张：把一个范围明确的业务问题变成「确认口径 → 只读查询 → 指标结果 → 证据引用 → 可导出报告」，降低核对成本，并把不确定条件显式暴露。

## MVP 取舍

选择单一合成 SaaS 数据集和 7 类明确指标：净收入、毛收入、退款金额、订单数、席位数、退款金额占毛收入比例、退款订单占比。支持产品、渠道和两个期间的比较。这样可以建立可独立验证的业务基线，而无需宣称连接了真实客户的数据仓库。

选择受约束 `query_sales` 工具调用；模型决定允许范围内的调用顺序，工具生成参数化 SQL。优点是指标定义、查询表与期间固定，可复核访问边界；代价是不能回答任意 SQL、用户自定义指标或跨表临时分析。更复杂的 Agent 框架暂时不会改善这组有限状态的核心验证，因此实现使用标准库。

默认离线规则模式，便于无密钥演示。真实模型模式单独配置，不会把规则模式包装成真实大模型，不会在模型失败后伪装成功。最终文字由工具证据生成，因此模型的未执行数字不会进入报告。

## 用户流程和状态

首页输入问题或点选示例 → 可选明确筛选 → 选择引擎 → 提交。

- `idle`：展示数据范围、合成标识和示例。
- `running`：禁用重复提交，显示执行中。
- `needs_clarification`：缺年份、缺比较期间、缺收入口径、缺退款分母或数据越界时停止查询；用户补充问题/筛选后重新提交。
- `completed`：展示当前期间 KPI、比较图表、结论、绑定引用、SQL/参数/原始返回、追踪、导出。
- `error`：模型未配置、超时、响应不兼容、预算耗尽或服务故障；明确报错，不生成分析结论。

目前澄清需要重新提交，不是会话记忆补槽。分析记录是可回看结果的本机列表，不承担多人协作和任务队列。

## 关键决策

1. **明确分母**：退款金额占比和退款订单占比分别展示；不指定分母时先澄清。零分母显示缺失而不是 0%，比率比较使用百分点。
2. **明确时间**：支持带年份年月、季度和闭区间日期；“最近”“上个月”、缺年份的比较不擅自假设。
3. **数字有引用**：所有结论和表格行指向本次执行的 Q 编号；点击跳转具体 SQL。导出包含相同参数和返回结果，便于第三方复核。
4. **结果与原因分离**：只回答可由字段直接统计的事实；没有流量、曝光和客户字段，不输出“渠道效率下降”或因果解释。
5. **只读与可控失败**：只读连接之外还使用 authorizer、表/函数白名单、行数/计算预算和本机访问校验；模型上限 6 步，失败没有结论。

## 验收标准

离线链路不依赖第三方服务即可完成三个演示路线。手工 4 单夹具应得到 9 月毛收入 90,000 分、退款 20,000 分、净收入 70,000 分、3 笔订单和 6 个席位；两种退款占比分别为 2/9、2/3。分组金额和笔数之和须与总览相等。

所有展示结论的引用必须存在且指向该次执行的查询。按订单日期归属退款和合成标识始终可见。日期/分母模糊时 SQL 数量为零。SQL 写入、附加库、系统表、扩展加载、多语句、危险函数和递归须拒绝；拒绝后源订单数量不变。

真实模型适配器须用本地 HTTP 桩证明工具调用、返回值传递、逆序执行、重复/错误参数/非 JSON、未执行数字、超时和重定向等路径。此验收不等于真实模型效果评估。界面须在桌面和窄屏可用，支持引用跳转、历史回看和报告导出。

## 产品验证计划（尚未执行）

招募 5–8 名运营/产品/分析人员，先做不展示产品的访谈，再使用指定业务任务做可用性测试。访谈提纲：最近一次渠道/退款分析是什么；当前从问题到答案涉及谁；曾有哪些分母或日期理解不一致；验证一个 AI 数字需要哪些来源；什么情况下愿意用导出结果；什么查询必须升级给分析师。

任务：比较指定月份渠道净收入；解释两种退款率的差异；复核一条结论的期间与分母；发现模糊期间并修正。记录任务完成率、数字/口径错误率、到首个正确答案的时间、引用复核是否完成，以及严重失败原因。不用“觉得有用”替代实际任务结果。未来目标阈值应由基线任务结果和业务风险讨论后确定，本文不编造提升比例。

## 指标与埋点设计（方案，未接遥测）

核心质量指标：可复核正确答案率。分母为一组人工定义且存在明确期待值的业务任务；分子必须同时满足数字、期间、口径与证据一致。拆分澄清正确率、越界拒绝率、工具执行错误率、引用覆盖率。

效率指标：从提交到正确答案耗时、模型工具步数、模型调用 token/费用（需供应商 usage）、重试次数。产品指标：用户任务完成、二次查询和导出行为。当前 run.elapsed_ms 和 trace.at_ms 只提供本机工程时序，不能替代用户完成时间，也没有真实模型 token 费用数据。

事件草案：`analysis_submitted`（引擎、问题长度、指标类型）；`clarification_required`（date/metric）；`tool_completed`（查询 ID、行数、耗时、拒绝原因）；`analysis_completed`（指标、期间、查询数、总耗时）；`citation_opened`（Q ID）；`report_exported`（格式）；`analysis_failed`（错误类别）。未来埋点不记录原始问题、密钥或真实业务数值，除非另行取得合法业务授权。当前代码没有远程遥测，仅保存本机演示记录。
