# SupportFlow 知识导入、维护与审核指南

## 一次完整操作

在“知识库与版本”下载示例 JSON，或直接使用 [data/import-example.json](../data/import-example.json)。替换为合成或授权脱敏的客服政策，选择文件或粘贴文本，再点击“校验并导入”。

导入成功后，资料清单显示来源、地区、版本、生效时间和当前状态。回到工作台输入问题，展开“检索证据”核对引用，再编辑、保存和审核。政策变化时发布新版本或停用，之后重新生成待审核草稿。

## JSON 格式与 12 个必填字段

导入对象仅包含 `documents` 数组，一次可导入 1–100 份资料。一个完整示例：

```json
{
  "documents": [
    {
      "id": "CUSTOM-001",
      "title": "项目空间归档政策",
      "category": "archive",
      "source": "合成政策手册 / 项目空间归档章节",
      "region": "all",
      "version": "1.0",
      "updated": "2026-10-18",
      "active": true,
      "effective_from": "2026-10-18",
      "effective_to": null,
      "keywords": ["归档", "归档空间", "archive"],
      "statements": [
        "工作区管理员可在项目空间设置中申请归档。",
        "归档后的项目空间只读；恢复访问需要管理员核验。"
      ]
    }
  ]
}
```

- `id`：稳定资料编号，1–80 字，只允许字母、数字、下划线、点和短横线，以字母或数字开头。更新时保持同一编号。
- `title`：资料标题，1–200 字。
- `category`：主题标识，1–80 字；同一业务主题使用一致标识，便于问题覆盖和冲突检查。
- `source`：可回查的来源文件、章节或地址，1–1000 字。
- `region`：`all`、`mainland` 或 `overseas`，分别表示全部地区、中国大陆、海外。
- `version`：非空版本编号，1–80 字。版本是业务标识，同一编号下不可重复。
- `updated`：资料更新日期，格式 `YYYY-MM-DD`；新版本不得早于当前版本的更新日期。
- `active`：必须明确填写布尔值 `true` 或 `false`。
- `effective_from`：开始生效日期，格式 `YYYY-MM-DD`。
- `effective_to`：最后有效日期，格式 `YYYY-MM-DD`；没有结束日期也必须填写 `null`。
- `keywords`：1–100 项非空字符串数组，每项最多 100 字。为自己的资料填写客服常用问法或术语。
- `statements`：1–200 项完整政策条款，每项最多 4000 字；把适用人群、前提、限制和例外保留在同一条款中。

字段名区分大小写。缺失字段、类型错误、无效日期、空条款或额外字段都会定位提示，例如 `documents[0].source：缺少必填字段`。同一批次不能重复导入相同资料编号，整个批次校验通过后才会原子写入。

HTTP 导入请求上限为 256,000 字节，因此实际批次大小也受正文长度限制。建议按主题分批维护。

## 更新、停用与有效期

每个编号只保留一份当前版本供检索判断。打开资料的“编辑新版本”，修改完整内容并填写未使用过的版本编号。保存后，旧版本立即标为被替代，原文与版本历史继续保留。

停用会让当前资料退出检索，并记录停用事件。重新启用需要发布新版本。资料状态由中国标准时间当日、更新日期与有效期共同决定：

- `active`：已启用，更新日期和开始日期不晚于当天，结束日期为空或尚未超过。
- `scheduled`：更新日期或开始日期在未来，暂不参与检索。
- `expired`：当天已超过结束日期，退出检索；结束日当天仍有效。
- `inactive`：手动停用或被新版本替代。

结束日期不得早于开始日期。发布未来生效的新版本也会立即退出旧版本，系统不会自动回退使用更早版本；需要连续服务时，请在新政策生效时发布。

历史工单保存生成时的来源和版本，后续修改资料不会重写历史。批准待审核草稿时会检查知识修订号，资料有任何更新都要求重新生成；即使修订号没有变化，引用跨日过期也会被拦截。

## 检索时如何使用资料

先根据地区、当前版本和有效期筛选资料，再按各个问题的关键词与维护的同义表达匹配，以 BM25 排序。自定义主题可以直接通过自己的 `keywords` 参与检索。

资料的 `statements` 对应逐条引用。例如第一条引用为 `[CUSTOM-001 §1]`。系统检查原文、引用编号、版本、地区和有效期，并核对每个问题是否有对应主题与常见问法的支持。来源真实但未覆盖全部问题时，返回澄清或人工核验动作。

地区限定资料需要明确地区；重叠地区、同主题资料出现数值或支持/不支持差异时会进入冲突处理。清理冲突时应由资料维护者确认权威版本，更新或停用后重新生成。

## 编辑、审核与回收问题

“保存编辑”保留当前正文、问题标记和备注，工单继续处于待审核状态。可以多次保存，每次轨迹都有相应正文与时间。批准、转人工和退回也保留人工修改，不会因非批准操作丢失文案。

原因可多选，对应服务端稳定标识：

- `source_not_applicable`：来源不适用。
- `missing_condition`：遗漏条件。
- `incomplete_answer`：回答不完整。
- `unsupported_claim`：依据不支持回复。
- `other`：其他，建议在备注中说明。

“处理轨迹 → 导出问题样例 JSON”导出已有保存或审核操作的工单，包含脱敏问题、原稿、当前稿、批准稿、生成结果、引擎/检索/知识版本、来源版本和逐次审核记录。常见邮箱、手机号与显式密钥字段会隐藏。将样例整理为固定评测集时，需再标注期望路由、适用资料与应保留条件，避免直接把历史审核操作当作标准答案。

## HTTP 接口

读取接口：

- `GET /api/session`：会话令牌、模型配置状态、知识修订号及审核原因标签。
- `GET /api/knowledge`：当前各编号最新版本、全部历史、修订号、快照日期与资料状态。
- `GET /api/knowledge/{id}/history`：`{id, versions: [...]}`，版本按最早到最新返回。
- `GET /api/review-examples`：可整理为下一轮评测的数据导出。

写入接口均接受 JSON 对象，并沿用本机会话的 Host、Origin 与 `X-CSRF-Token` 校验：

- `POST /api/knowledge/import`：正文为 `{"documents": [完整资料对象]}`。
- `POST /api/knowledge/{id}/versions`：正文为 `{"document": 完整新版本对象}`；也兼容直接传完整资料对象，`id` 可省略但不能与路径冲突。
- `POST /api/knowledge/{id}/deactivate`：正文为 `{}`。
- `POST /api/tickets`：正文包含 `title`、`content`、`region` 和 `mode`。
- `POST /api/tickets/{id}/review`：正文包含 `action`、`draft`、`note`、`reasons`；`action` 为 `save`、`approve`、`escalate` 或 `reject`。

知识写入成功返回最新快照；字段错误返回 400 和具体提示，不存在的资料返回 404。待审核工单返回 `current_draft`、`review_reasons` 和 `audit`；每次事件的 `details` 保存正文、问题标记、备注与版本信息。

读取结果中的 `eligible`、`current_status`、记录时间和替代信息是展示字段，不能原样放回导入对象；发布新版本只提交上述 12 个字段。

## 本地存储与结果复核

- `data/knowledge.json`：随代码交付的合成种子资料。
- `work/knowledge.json`：首次维护后生成的用户资料、版本历史和维护事件，使用临时文件后原子替换保存。
- `work/supportflow.sqlite3`：工单、生成结果、编辑和审核记录；原有 v1 数据库会增量迁移。

首次启动且没有用户资料文件时使用种子资料。日常重启会保留已维护资料与工单，二者独立于源码。评测定义与版本对比见 [EVALUATION.md](EVALUATION.md)。
