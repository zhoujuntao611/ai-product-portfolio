# SupportFlow 产品需求说明 · v2

## 产品问题与目标

客服回复不仅需要找到一份看起来相关的文档，还要确认版本是否有效、客户属于哪个地区、条件是否满足，以及一张工单中的多个问题有没有遗漏。政策更新后继续使用旧稿，会让检索质量问题直接进入客户回复。

SupportFlow 的目标是让使用者能够导入自己的客服政策，输入问题后得到**有具体依据、可逐条核对、可保留审核轨迹的回复草稿**。目标用户是一线客服和负责维护政策、复盘回复质量的业务负责人。

本次沿用现有 v1 应用：工单工作台、规则生成、可选模型证据选择、SQLite 与审核状态机均在原代码上扩展。内置政策与验收问题为合成资料，真实模型效果和业务收益尚未测量；下一阶段用授权脱敏工单与客服访谈验证真实适用性。

## 迭代优先级与产品取舍

### P0：资料可用且可维护

提供一种低门槛导入方式：结构化 JSON 文件或粘贴文本。每份资料强制填写来源、地区、版本、生效状态与时间，并逐条保存政策原文。错误定位到字段，整批校验后一次保存。

按资料编号维护版本链；发布新版本即退出旧版本的当前检索，支持手动停用与历史回看。当前快照按中国标准时间当日计算，排除待生效与过期资料。待审核草稿保留知识修订号，政策变化后重新生成再批准。

选择 JSON，是为了让地区、版本与条款在导入时就明确，先完成资料生命周期。字段示例与约束见 [KNOWLEDGE.md](KNOWLEDGE.md)。

### P0：有引用，也要有支持

v1 已能按关键词召回政策并引用原文，主要失败点是同义表达漏召回、全局候选数量截断多问题，以及引用真实却没有回答完整问题。

v2 使用可维护的主题同义词、逐问题拆分和 BM25 排序，继续以地区、版本、启用状态和有效期作为适用门槛。按每个问题检查来源覆盖，避免“有一条相关资料”被当成整张工单已解决。

证据检查核对条目原文、引用编号、来源版本、地区及有效期；入口、时间和数量问法增加支持检查。规则模式引用完整条款保留限制条件；模型模式沿用现有条目选择接口，检查后同样使用本地原文组装。缺少资料时给出澄清问题或人工处理动作。方案比较见 [RETRIEVAL.md](RETRIEVAL.md)。

### P1：审核结果可以回收

在批准、转人工和退回之外增加“保存编辑”，允许审核中途保存而不结束工单。每次处理记录修改正文、原因、备注、时间与内容指纹。

问题标记支持来源不适用、遗漏条件、回答不完整、依据不支持回复和其他。JSON 导出包含脱敏问题、原稿、修改稿、生成结果版本、来源及审核轨迹，用于筛选下一轮固定评测问题。

## 主要使用路径

1. 资料维护者导入政策，查看校验提示，确认适用地区与当前状态。
2. 客服输入 5–4000 字问题，选择地区与规则/模型模式。
3. 系统检查请求类型，拆分问题并检索当前有效资料。
4. 展示草稿、逐条引用、问题覆盖与资料版本；资料不足、地区矛盾或政策冲突时说明下一步。
5. 审核者核对原文与条件，编辑正文、标记问题并保存；随后批准、转人工或退回。
6. 维护者更新或停用资料，审核者导出问题样例，整理固定集并重新运行对比。

## 状态与审批规则

每次生成创建 `DRAFT` 工单，结果区分 `ready`、`needs_context`、`conflict`、`refused`、`escalate` 和 `unknown`。

- `save`：保持 `DRAFT`，保存当前草稿、问题标记与备注，并新增 `DRAFT_EDITED` 轨迹。
- `approve`：仅允许有据可答且正文非空的待审核工单进入 `APPROVED_LOCAL`。批准前再次确认知识修订号与引用版本；引用停用或超出生效期时要求重新生成。
- `escalate` / `reject`：分别进入 `ESCALATED` / `REJECTED`，保留人工修改正文和处理原因。

人工修改标记为未自动验证，由审核者确认新增内容与引用。已完成审核的工单保留原始记录，补充信息后创建新工单。所有状态只保存本地处理结果。

## 异常场景设计

- 同义表达：如“报销凭证”“进不了账号”，通过维护的主题表达扩展召回。
- 多个问题：按问题展示覆盖情况；一个问题没有依据时要求补资料或拆分处理。
- 地区不明确：地区限定政策要求先确认地区；退款的大陆与海外条款分别呈现，避免合并适用。
- 正文与地区选择矛盾：停止草稿事实输出，提示修正上下文。
- 政策冲突：检测同主题、重叠地区的数值或支持/不支持差异，交给政策负责人核验并维护资料。
- 企业合同例外：标准订阅条款不能替代合同核验，转客户经理确认。
- 未覆盖能力、高影响操作与越权请求：分别引导补资料、人工核验或拒绝处理。
- 模型连接或格式异常：返回可解释错误；空证据或不支持问题的选择不进入批准流程。

## 核心验收标准

1. JSON 缺少来源、地区、版本或状态等字段时返回明确字段提示，批次中的任何错误都不产生部分导入。
2. 自定义资料导入后立即参与检索并生成具体引用；发布同编号新版本后只使用新版，停用后退出检索，历史仍可查看。
3. 生效时间边界正确：开始日前与结束日后不参与检索；结束日当天仍有效。
4. 发票、登录等标准问题使用适用依据；同义表达能够召回对应主题。
5. 大陆和海外政策按客户地区适用；未知地区、上下文矛盾、同范围冲突按预期澄清或人工核验。
6. 多问题逐项检查，未覆盖问题不会被已命中的主题掩盖；引用检查同时覆盖原文、版本、地区与有效期。
7. 保存编辑、批准、转人工及退回均保留正文与轨迹；刷新后能读取，终态不能重复审核。
8. 资料更新、停用或跨日过期后，旧稿批准被拦截，已保存编辑仍可回看。
9. 审核原因经过服务端校验；导出包含问题、前后文案、引擎与知识版本、来源版本及处理记录，常见邮箱、手机号与显式密钥隐藏。
10. 没有密钥时完成规则模式与模型适配器契约测试；请求大小、静态文件、Host/Origin/CSRF 与前端文本渲染边界保持有效。

## 评测与后续验证

保留 v1 实现和知识快照，在同一固定问题集上比较当前关键词基线与 v2。逐题记录政策适用性、引用支持、澄清与转人工判断，保存预期、实际结果、失败原因和实现/资料版本。原有 31 条回归集与历史报告继续保留，详细口径见 [EVALUATION.md](EVALUATION.md)。

下一轮先从审核导出中筛选典型失败，再独立标注新问题，区分开发回归集与后续验证集。业务验证关注查政策到合格草稿的用时、原样采用/小改/重写占比和升级原因；真实模型测试需记录服务商、模型版本、提示版本、成本与人工评分。

## 当前产品边界

当前交付聚焦单机资料治理、证据草稿和人工审核闭环；外部客服渠道、多人权限与自动执行属于后续集成。规则检查覆盖可说明的同义表达、问法与冲突形态，复杂合同和语义例外由审核与问题回收继续完善。
