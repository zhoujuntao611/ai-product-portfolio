# SupportFlow：问题、决策与验证记录

本记录对应 2026-10-19 对**本地 v2.0**的审阅与 v2.1 修复。项目使用合成政策和问题，本轮未进行客服访谈或真实用户试用，未外呼真实模型。这里的“问题来源”是代码审阅与可复现输入，不应改写成用户调研结论。

## 1. 先确认版本，避免重复计算已有成果

此前审阅引用 GitHub 旧版；本地 v2.0 已经增加资料导入、版本治理、逐问题检索、编辑保存和问题样例导出。首次重跑，原有 **109 项工程测试全部通过**，记录见 [修复前工程记录](../verification/review-before-engineering.txt)。

“转人工或拒绝丢失编辑稿”在这个本地版本已经修复。本轮分别检查终态、重新读取、审核事件和导出，两个路径均通过。批次导入原子性、资料更新拦截旧稿也已通过。本轮给它们增加可重复的验收记录，**不将已经通过的能力记为新修复收益**。

修复前的 `core.py`、`server.py`、`knowledge.py` 和两份知识/配置按原始字节冻结到 [baseline_v2_0](../eval/baseline_v2_0/manifest.json)，复现脚本先检查 SHA-256 再运行。该基线与早先 `5aef4cc` 的 v1 基线是两条独立比较。

## 2. 发现了什么问题，为什么先修这些

**优先修复：有来源，但来源回答的是另一个问题。**

- 问“中国大陆标准订阅退款多久会到账”，v2.0 将“首次付款后 7 个自然日内提交退款申请”当作支持，生成可批准草稿。申请窗口、审核耗时和到账耗时是不同事项。
- 问“导出任务多久能完成”，v2.0 用“文件保留 24 小时”通过时间支持检查。保留时长无法回答生成时长。
- 问“API 每月多少次”，v2.0 用“每分钟 60 次”直接完成。按分钟的速率限制无法证明按月额度，也不能默认允许将它相乘换算。
- 模拟模型即使面对含到账时效的资料，只选申请窗口条款时，原版本仍会通过。因此检查必须作用于**模型实际选中的条款**，不能只检查候选资料有没有这项事实。

这些错误会给审核者“已经核对依据”的误导，优先于增加新的功能入口。

**随后修复：常见地区表述未被同一套规则处理。**

- “大陆工作区”“大陆用户”“国内用户”“中国内地”未能推断为大陆，造成重复澄清。
- 正文写“大陆工作区”，下拉选择海外，v2.0 没检测到矛盾，直接输出海外 14 天政策。
- “不是海外的工作区”被当作海外正向表述。否定一个地区并不能确定实际地区，需要澄清。

**流程修复：快速连续生成后，历史列表顺序不稳定。**

本轮浏览器验收暴露了同秒生成多个工单时，列表没有明确的次序保证。服务端时间精度为秒，仅按创建时间倒序无法区分同秒记录。修复为创建时间倒序、同秒按插入顺序倒序；构造同一时间戳的三条工单，通过真实 HTTP 列表验证新工单排在前面，并为历史按钮加入稳定工单标识。

## 3. 比较了哪些方案，为什么这样选

对“来源不支持所问事项”，考虑三种处理：

1. 只把“任何时间数字”门槛调得更严：改动小，但仍无法区分申请窗口、审核、到账、生成和保留。
2. 增加可解释的事项与周期门槛：在实际选中条款内核对所问事项及时间表达，明示每月/每分钟等周期；没有明确支持则澄清。可离线复现，适合当前小型政策库。
3. 增加真实模型语义判定：可能覆盖更多改写，但需要新的带标注样例、供应商验证、成本和延迟测试，模型自身也可能误判。本轮未实现或测量这一方案。

选择第二项。它直接覆盖本轮已复现的高影响错误，同时保留人工审核。实现是显式规则，不能声称已解决开放域语义蕴含。正向对照包括补充真实对应条款后可回答，避免通过一律拒答获得高分。

对地区问题，选择复用同一组地区表达处理推断与矛盾检测，而非只给推断函数补一个词。否定表述保守进入澄清，避免凭“不在海外”猜测“在大陆”。

知识接入仍使用带来源、地区、版本、有效期的结构化 JSON；现阶段先保证资料治理与可溯源。检索仍为同义表达、逐问题词法召回和 BM25 排序，未宣称做过向量方案实测或 BM25 单项消融。

## 4. 交付了哪些修改

- `core.py` 升级至 `supportflow-v2.1`：共享地区表达、否定与多地区澄清、实际选证的事项/周期支持门槛。
- 新增 [26 条固定审阅回归](../eval/review_cases_v2_1.json)：21 条问答验收，覆盖失败输入和正向对照；5 条导入、版本、审核及导出工作流检查。
- 新增 [复现脚本](../verification/review_regression.py)：同题运行冻结 v2.0 与当前版本，保存完整实际回答、预期、失败原因、实现/问题集哈希。两道选证题使用本地模拟响应，真实模型调用数为 0。
- 新增 9 组针对性工程测试，保留原有测试与知识生命周期实现。

本轮代码审阅、方案整理、实现和自动验收由 AI 编程协作完成。项目作者可据此复核产品取舍并复现实验；没有证据支持将上述过程描述为其独自手写实现、独自执行测试或已经完成真实用户调研。

## 6. 下一轮如何验证实用性

待获得合成以外的授权脱敏资料和真实客服试用条件后，再开展以下工作：

1. 冻结本次未参与修改的工单样本，分别标注地区适用、所问事项、必要条款和合理的澄清/人工路径。对资料不足的题，拒答正确与有据可答应分开报告。
2. 用相同资料、相同问题和相同模型选择结果比较规则与模型判定，记录端到端结果、真实调用耗时、成本与错误原因；不能把模拟协议测试当成模型理解能力。
3. 让试用者完成“导入一份政策—生成—更新政策—审核—导出问题”任务，记录任务是否完成、卡点、人工修改和处理用时。需实际招募和执行后才能填写人数、时长和收益。
4. 从导出样例中人工复核错误，确认期望结果后加入下一版开发集；另保留未参与修复的验收样本，避免反复在同题上优化后称为泛化提升。

当前结论：本轮证明了具体缺陷可复现、方案有取舍、修改有回归证据；尚不能证明开放问题覆盖率或真实客服业务收益。
