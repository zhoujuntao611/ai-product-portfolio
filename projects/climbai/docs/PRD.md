# ClimbAI —— AI 攀岩训练助手

> 早期规划存档：ClimbAI 现作为攀岩方向的规划与反馈原型保留，当前主项目为[攀迹](../../panji/README.md)。本文记录当时的产品方案，不代表攀迹已经实现了这些能力。[当前项目关系](../../../docs/CLIMBING_EVOLUTION.md)

**项目主张：设计一个以训练目标为起点，能调用知识与训练记录、维护个人画像、根据反馈调整计划的 ToC AI Coach Agent。**

本文记录项目立项时的产品方案与完整 PRD 框架；后续实现状态和实测工程结果以 README 与 docs/VALIDATION.md 为准。真实访谈、云端 Figma 文件、教练审核和真人试用仍待完成。文中的用户画像、痛点、研究工期及效果验收数值是待验证假设或建议目标；示例数据是模拟数据。

## 一、产品定位

### 1.1 一句话介绍

ClimbAI 面向室内抱石爱好者，根据训练记录、个人目标与可用时间建立能力画像，生成有依据的训练计划，并通过训练反馈持续调整。

产品应让用户更容易回答三个问题：今天练什么？为什么练这个？练完之后下一次怎么调整？

### 1.2 在作品集中的位置

- SupportFlow：体现企业客服场景、知识工作辅助与业务效率判断。
- MetricPilot：体现企业数据分析、工具调用与任务执行。
- ClimbAI：补充消费端的首次体验、个性化、使用负担、用户信任、持续使用和反馈闭环。

面试时的重点是 ToC 产品判断与可验证的 Agent 设计。代码量、节点数量和模型参数不作为项目价值的主要证据。

### 1.3 首批用户画像

MVP 聚焦 **18 岁以上、接触攀岩约 0–12 个月、主要进行室内抱石、每周约 1–2 次训练、希望进步但缺少系统训练习惯的用户**。这些范围是招募与产品收敛假设，需要访谈验证。

示例用户“小林”：工作或学习之余去岩馆，能完成一部分入门线路，刷难线时反复失败；会搜索技巧，但不知道哪些建议适合自己，也不想每次花十分钟记录训练。

辅助场景：已有一定经验、遇到平台期，但尚未固定接受教练指导的用户。MVP 暂不扩展到竞赛训练、儿童、室外领攀或伤后康复。

等级输入需同时记录等级体系、岩馆和稳定完成范围。最高完成等级只能辅助理解背景，不应直接用于跨馆排名或认定力量、耐力水平。

### 1.4 用户痛点与待验证假设

1. **训练决策困难**：到馆后随机刷线，缺少明确训练重点。待验证：用户是否比“缺少知识”更在意“今天怎么安排”。
2. **失败经历难以转为行动**：知道自己没有完成线路，却不确定是脚法、读线、疲劳还是线路选择问题。待验证：结构化复盘是否比普通记录更有用。
3. **通用建议难以适配生活**：计划没有考虑时间、场地与最近状态。待验证：低负担改期与调整是否提高执行意愿。
4. **反馈与记录成本高**：记录后看不到下一次训练会发生什么变化。待验证：展示调整依据是否提高反馈提交率。

研究方法：先访谈 6–8 名目标用户，询问最近一次真实训练、训练决策方式、放弃记录的原因与计划中断经历；请 1 名具有实际攀岩教学经验的教练审阅需求、练习模板及关键边界。保留原始记录、洞察、反例和需求优先级，不用虚构访谈代替证据。

### 1.5 核心价值与差异化

- 将零散训练描述转成下一次可执行的训练重点。
- 将个人时间、目标和状态整合到计划中，减少决策负担。
- 展示每条建议的依据、适用条件和不确定性，便于用户纠正。
- 让训练记录直接影响后续计划，形成持续使用的理由。

竞品核验表明，Crimpd+ 已提供专家训练库、针对弱项的 Skill Templates、自定义计划和计划调整；KAYA 已支持尝试、完攀及训练记录。因此差异化应定位为 **中文初阶抱石场景中的低负担反馈、可追溯画像和可解释调整**，并进一步验证需求。不能声称现有产品没有计划能力或整个市场缺少 AI 功能。[Crimpd+ 官方介绍](https://www.crimpd.com/crimpd-plus/)、[KAYA 官方记录指南](https://kayaclimb.com/support-articles/logging-your-climbs-on-kaya)。

## 二、MVP 功能设计

保留四项核心功能，所有功能服务同一个训练闭环。首页以行动为中心，知识聊天作为训练解释入口。

### F01：AI 攀岩能力画像｜P0

**用户任务**：理解当前可以优先观察和改进什么。

输入：训练经历、稳定完成范围、目标、可用时间、近期不适情况、可选自评和最近训练记录。首次不强制收集身高、体重、性别；无等级经验允许选择“暂不清楚”。

画像维度：脚点控制、身体协调、读线与动作选择、持续攀爬体验、训练习惯。没有测量数据的力量或耐力指标显示“未知”，不生成科学分数。

每个维度展示四层内容：

- 事实观察：例如最近三次记录都提到脚点滑落。
- 用户自评：例如自认为脚法是主要问题。
- AI 假设：脚点控制可能值得优先观察。
- 证据充分度与下一步：当前证据有限；下次训练补充容易线路与困难线路的差异。

首次输出标注“基于自评的初始画像”。允许用户纠正推断，保留来源与版本。避免未经校准的置信度百分比和雷达图评分。

**AI 价值**：理解自然语言卡点、合并多次记录、区分观察与推断、提出后续验证问题。问卷计分、记录统计和数据保存由代码完成。

验收：所有假设关联证据或明确标记为自评；信息缺失不生成结论；矛盾记录优先追问；用户纠正能进入新画像版本。

### F02：个性化训练计划 Agent｜P0

**用户任务**：获得一周内可执行的计划，明确每次到馆的重点。

输入：目标、画像、时间预算、场地与器材、近期训练状态、审核后的练习库和知识证据。

输出：一周安排与当次训练卡。训练卡包括目标、练习步骤、预计时长、适用条件、休息提示、停止条件、安排理由和来源。计划从经教练审阅的练习库中选择与组合，避免让模型自由发明高风险动作、强度或训练负荷。

目标优先写成可观察的过程，例如“建立每周到馆与训练后复盘习惯，针对脚点选择进行记录”；攀爬等级提升可作为用户愿望，不作为系统保证。

用户可修改时间和目标，查看计划变化后确认生效。改期、时长求和与器材检查采用确定性规则；语义理解、练习选择与解释由模型辅助。

**AI 价值**：根据多项个人约束选择训练重点，解释取舍，并在目标冲突或信息不足时追问。

验收：时长不超过用户预算；练习 ID 必须来自审核库；器材与适用条件匹配；每次任务有明确目的；计划通过校验后才可确认。

### F03：攀岩知识 RAG 助手｜P1，精简纳入首版

**用户任务**：理解当前训练卡和复盘中的问题。

入口：训练卡中的“为什么这样安排”“怎么做”；另提供知识助手页。优先支持动作技术、训练组织、记录方法和恢复原则，不扩展成全领域攀岩百科。

知识库建议以 20–30 个经审核的短知识条目和 10–15 个低风险练习模板起步。资料具有来源标题、URL、更新时间、段落 ID、适用人群和场景标签；自编内容明确注明。公开网页作为参考时，优先保存链接和必要短摘录，尊重资料使用许可。

回答展示结论、执行说明、适用条件和来源卡片。找不到可信依据时，明确资料不足；涉及伤病诊断或康复处方时不生成处方。

**AI 价值**：把检索证据与当前用户目标结合，解释“这条知识与你有什么关系”。向量检索和来源校验可以由工具直接完成，不要求额外调用模型。

验收：引用 ID 与数据库匹配；引用内容支持回答；库外问题正确说明不足；检索片段中的指令不能改变系统行为。

### F04：训练记录与反馈调整闭环｜P0

**用户任务**：花较少时间复盘，并看见下一次计划如何改变。

训练记录默认选择项：完成 / 部分完成 / 跳过、实际时长、主观难度、主要卡点、是否出现不适；自由文字和单条线路详情为可选。可按稳定完成范围或训练主题汇总，不要求逐条录入所有线路。

“结束训练”先独立保存训练完成事件，再进入反馈表单。用户关闭反馈表单时仍保留完成事件；试用期间用简短训练日记核对漏记训练，避免只统计提交反馈的训练。

反馈报告展示：实际发生了什么、可能原因、证据不足的地方、原计划与建议修改项、调整理由。用户接受后形成新计划版本；用户拒绝时保存原因。

调整类型包括保持计划、改期、缩减内容、替换练习、补问或暂停相关任务。单次训练成功不自动提高强度；一次未完成也不直接判定能力下降。反馈不改变模型参数，改变的是用户记忆与后续计划。

**AI 价值**：识别“时间不足”“任务偏难”“疲劳”“技术卡点”的差异，关联历史记录并提出有依据的调整。

验收：报告基于真实训练记录；没有记录时不伪造反馈；修改前后可追溯；不适反馈进入暂停相关建议的分支。

### 2.5 视觉分析与范围取舍

MVP 暂缓视频动作分析。多模态视频摘要可以快速演示，但可靠的动作纠错需要处理机位、遮挡、墙面角度、身体与岩点对应、数据标注和教练评测，还增加上传、存储和隐私处理。当前缺少标注与评测条件时，无法可靠验收自动动作评分。

V2 可考虑“视频辅助复盘”：用户标记卡住的片段，系统生成待本人或教练确认的观察问题。进入条件是文本反馈闭环已被试用证明有价值，且获得可使用的视频样本、教练审阅与清晰的失败边界。

首版也不纳入社区、支付、岩馆合作、可穿戴设备、路线自动识别、复杂消息推送和全套账号体系。作品集演示可以使用隔离的测试用户；进入多人试用前补充必要的身份与权限校验。

## 三、AI Coach Agent 架构

### 3.1 产品层与技术层

产品层是一个 AI Coach Agent，围绕用户目标完成训练决策。技术层实现为四个逻辑节点与受控的条件工作流，使用有限工具和持久状态。检索节点可以是确定性程序，不必四个节点各跑一个模型，也不部署四个自主协商的服务。

这种设计可以展示工具调用、任务规划、长期记忆、结构化输出与反馈优化，同时明确哪些决策由代码控制。LangGraph 官方区分预先定义路径的工作流与动态决定流程的 Agent；本项目采用受控工作流实现 Coach 产品。[LangGraph 官方文档](https://docs.langchain.com/oss/python/langgraph/workflows-agents)。

共享状态包含目标、画像版本、必要记录、检索证据、计划草案、不适标记、当前状态和下一步行动。节点可以在许可范围内决定追问、补充检索、生成草案、保持计划或提出调整；检索与修复次数受上限控制。作品集应展示真实的条件分支、工具输入输出和状态变化，而非只展示四段提示词。

### 3.2 首次规划路径

用户输入 → 输入检查 / 缺信息追问 → 用户画像 Agent → 知识检索 Agent → 训练规划 Agent → 规则校验 → 用户确认 → 保存计划 v1。

首次没有训练反馈，不能直接运行反馈优化生成虚构结论。

### 3.3 训练后路径

训练记录 → 不适与异常分支检查 → 反馈优化 Agent → 更新画像 → 按需检索与规划 → 规则校验 → 展示修改及依据 → 用户确认 → 保存计划 v2。

不适反馈由后端规则立即标记相关任务暂停，首页停止推荐相关任务，并提示专业咨询；后续计划修改由用户确认。缺少证据时追问或保持计划。知识问答采用“问题 → 检索 → 有引用的回答”短路径。

### 3.4 四个 Agent 的职责与接口

**用户画像 Agent**

- 输入：档案、目标、近期训练记录、用户对已有画像的纠正。
- 职责：抽取事实与约束，形成带证据的能力假设，识别缺失信息。
- 工具：读取档案、读取必要历史、生成画像快照。
- 输出：`profile_version、dimensions、evidence_ids、evidence_level、missing_fields、constraints`。

首次建档可调用模型生成初始画像；反馈阶段优先校验并合并反馈 Agent 返回的 `profile_patch`，保存新快照，无须再调用模型。节点执行次数和模型调用次数分别记录。

**知识检索 Agent**

- 输入：候选训练重点、问题、经验与场地条件。
- 职责：检索审核资料与练习，过滤不适用内容，返回证据状态；必要时改写查询一次。
- 工具：知识向量检索、来源读取、练习库查询。
- 输出：`chunk_ids、source_urls、exercise_ids、applicability、evidence_status`。

**训练规划 Agent**

- 输入：画像、目标、时间预算、检索结果和业务约束。
- 职责：选择训练重点、组装当次与一周任务、解释安排、提出冲突解决或补问。
- 工具：读取审核练习库、校验计划、输出计划草案。
- 输出：`sessions、exercise_ids、duration、rationale、citations、profile_version`。

**反馈优化 Agent**

- 输入：计划版本、完成情况、主观难度、卡点、历史反馈。
- 职责：比较计划与执行，提取观察和假设，提出画像修订与计划调整。
- 工具：读取计划与记录、计算完成统计、提交调整草案。
- 输出：`observations、hypotheses、profile_patch、adjustment_proposal、reason、risk_flags`。

### 3.5 记忆与边界

- 业务事实存 SQLite：用户档案、原始训练记录、目标、画像快照和计划版本。
- 知识索引存 Chroma：经审核的知识片段及适用条件。
- 模型上下文只读当前画像摘要、必要的近期记录与检索证据，不把所有聊天无上限拼接。
- 每条能力假设关联记录 ID；每次反馈关联原计划版本；每次新计划关联画像、知识与运行版本。
- 模型不能直接覆盖已确认计划、删除用户记录或访问其他用户数据。后端校验工具参数与用户权限。
- 不适信号优先于计划推进；不进行伤病诊断，不拟定康复处方。这是本产品的保守设计规则。

### 3.6 演示场景

模拟用户每周有两次到馆时间，反馈“这次只练了半小时，困难线路脚点经常滑，简单线路没有这个问题”。

1. 代码读取原计划、计算执行时长，识别时间预算变化。
2. 反馈 Agent 记录“困难线路中的脚点问题”这一观察，提出与难度有关的待验证假设，不直接诊断技术水平。
3. 画像节点校验并合并反馈给出的证据修订，不额外调用模型；检索返回适用的技术学习资料。
4. 规划 Agent 提议缩减下一次内容并明确记录重点；展示原计划和修改项。
5. 用户确认后保存新版本；用户不同意则保留原计划与拒绝理由。

演示重点是事实、依据与后续行动之间的关系，不能把模拟训练当作真实效果证明。

## 四、完整产品流程

### 4.1 首次进入

首页解释核心用途，提供“建立我的训练计划”。首次价值目标是快速看到与自己有关的训练安排。身份信息最小化，允许先体验模拟案例。

### 4.2 建立档案

分步收集经历、稳定完成范围、到馆时间、器材条件与近期不适。允许“不清楚”和跳过非必要问题。保存草稿。展示这些信息将怎样影响计划。

首次建档约 3 分钟、训练反馈约 1 分钟属于可用性体验目标，待测试验证。

### 4.3 制定目标

选择一个主要目标，补充可用时间与预期周期。AI 帮助将“想提高水平”转成可观察的训练行为。目标与时间明显冲突时，解释限制并让用户调整。

### 4.4 查看与确认计划

展示初始画像与一周安排，突出安排依据和待验证事项。用户可以改时间、纠正画像并确认计划。确认后首页展示下一次训练卡。

### 4.5 训练与记录

到馆查看练习步骤、目的和知识解释。完成后记录完成程度、实际时长、主观难度和主要卡点；可保存反馈草稿。中断或跳过允许选择原因，不用惩罚性文案。

### 4.6 反馈与调整

AI 输出事实摘要、解释和下次调整建议，用户接受、拒绝或补充信息。系统保存计划版本及理由。信息不足时说明不足，避免为了展示变化而强行修改计划。

### 4.7 持续使用

每周回顾已执行训练、反馈趋势与目标变化。强调行为与观察变化；在数据和场景不可比时不宣称能力提升。用户可以查看、导出和删除记录。

## 六、Figma 原型规划：八个页面

内容：已知事实、用户自评、AI 假设、证据来源和待验证事项。主操作“纠正画像 / 补充记录”。用分层条目展示，不用未经校准的能力评分。支持缺少记录和证据矛盾状态。

内容：一周安排、每次任务详情、时间、安排理由与引用。主操作“确认计划 / 修改时间”。支持时间不足、器材不匹配、信息不足和历史版本对比。

内容：当次练习卡、知识解释、完成程度、实际时长、难度、卡点及不适记录。主操作“完成并提交反馈”。支持部分完成、跳过、保存草稿和提交失败重试。

### P06 AI 反馈报告

内容：本次事实、解释、未确认假设、原计划与修改建议、修改依据。主操作“接受调整”；提供“保持原计划 / 补充信息”。支持无需调整、资料不足和不适暂停分支。

### P07 知识助手

内容：围绕当前训练的快捷问题、回答、来源卡片、适用条件。主操作“继续提问 / 返回训练”。支持检索无结果、引用不足和问题超出范围。

内容：目标、档案、训练历史、计划与画像版本、数据导出及删除入口。主操作“修改目标 / 查看历史”。支持空历史和删除确认。

### 原型组织

Figma 建议建立 Foundations、Screens、Flows、States 四个分区。使用移动端优先的画板和统一组件：训练卡、证据卡、状态标签、反馈选择项、修改对比。组件采用 Auto Layout，以便调整文案长度。

至少连通三个演示流程：首次建档到确认计划、训练后反馈到接受调整、不适反馈到暂停相关任务。知识解释作为分支返回训练页。开发前先用低保真原型验证信息是否易懂，再补高保真视觉。

## 七、技术实现方案

### 7.1 推荐架构

移动端优先 React H5 → Python / FastAPI → Coach 工作流服务 → LLM API + Chroma + SQLite。

- **React**：档案表单、训练卡、画像证据、记录、计划差异、知识引用和加载 / 失败状态。Demo 可复用成熟组件。
- **FastAPI**：身份与权限、参数验证、业务接口、运行状态和模型密钥管理。
- **LangChain + LangGraph**：模型 / 工具调用与四节点受控流程。两个框架不必再叠加 LlamaIndex；不熟悉 LangGraph 时可先用显式 Python 状态机，但保留相同接口与分支。
- **LLM API**：选择支持中文、结构化输出和工具调用的供应商；模型通过固定场景比较质量、延迟和成本后确定，不在规划中编造模型价格。
- **Chroma**：知识片段与元数据的本地持久索引。其 PersistentClient 适合本地开发测试；多人部署另评估服务器模式。[Chroma 官方文档](https://docs.trychroma.com/reference/python/client)。
- **SQLite + SQLModel**：业务事实、计划、记录和版本。FastAPI 官方提供对应的数据库集成示例。[FastAPI 官方文档](https://fastapi.tiangolo.com/tutorial/sql-databases/)。

### 7.2 最小数据模型

- User：测试用户 ID 与身份状态。
- Goal：目标、时间预算、周期和版本。
- ProfileSnapshot：画像、事实 / 假设、证据 ID、证据充分度及约束。
- ExerciseTemplate：审核练习、适用条件、步骤、来源与审核状态。
- PlanVersion / PlannedSession：计划版本、当次训练、使用的画像与练习、确认状态。
- TrainingLog：关联训练与计划版本、完成状态、时长、卡点、主观反馈。
- FeedbackReport：事实摘要、调整草案、理由、接受或拒绝状态。
- KnowledgeChunk：原文片段 ID、来源、URL、适用标签与知识版本。
- AgentRun：运行 ID、模型 / 提示词 / 知识版本、工具结果、校验、耗时与 token 用量。

画像与计划保存快照，原始训练记录保留。向量库不代替业务数据库，不把个人训练记录与公开知识混成无权限区分的共享检索库。

### 7.3 核心 API

建议最小接口：保存 / 读取档案；创建 / 修改目标；生成 / 获取计划；确认计划；提交训练记录；生成反馈；接受 / 拒绝调整；知识问答；读取运行状态；导出 / 删除个人记录。

以 `user_id、plan_version、session_id、run_id` 关联事实与运行。提交训练记录应处理重复请求，避免重复生成两份反馈或两次计入指标。

调整草案保存 `base_plan_version`；确认时检查当前版本是否仍一致，版本变化则重新生成草案或重新展示差异。使用 SQLite 事务更新确认状态和当前计划指针，避免旧草案覆盖新计划。

### 7.4 校验、异常与降级

1. Pydantic 校验输出结构；业务规则验证时长、练习 ID、器材、适用条件和真实引用。
2. 校验失败携带错误信息修复一次；仍失败不发布新计划，保留已确认版本。
3. 检索不足可以追问或重新检索一次；仍不足说明无法确认。引用必须由后端实际检索结果绑定，不接受模型自造来源。
4. 超时 / 限流采用有限重试；前端显示运行状态。首次生成失败可重试；若展示通用示例，明确注明“示例”。
5. 不适、诊断请求和资料中的提示注入有独立测试与分支；检索文本只作为资料。
6. API 密钥只保存在服务端。试用用户隔离数据并允许删除；运行日志避免不必要的个人敏感内容。

### 7.5 开发排期与成本

假设已经熟悉 Python、能复用前端组件、有可使用的知识资料并得到教练审阅支持：**约四周制作可演示 MVP，建议预留 80–120 小时；之后再安排两周试用**。这属于工期估算，初次学习相关框架需要增加时间。

- 第 1 周：访谈、范围收敛、Figma 原型、知识与练习库、数据契约。
- 第 2 周：画像、RAG、规划、校验与业务接口。
- 第 3 周：前端、记录反馈、版本对比、运行日志。
- 第 4 周：离线评测、异常测试、可用性测试与 Demo 整理。
- 第 5–6 周：通过测试后开展 8 人、14 天试用，整理证据与迭代。

单任务成本 = 输入 token × 输入单价 + 输出 token × 输出单价 + embedding 用量 + 相应部署成本。接入供应商后填入当时官方价格和真实账单。

首次画像 / 计划以约两次生成调用作为初始预算；反馈分析一次，确需重规划再加一次；知识问答一次。检索与规则无需每步调用模型。记录实际调用次数、重试率、每个完成任务的成本以及 P50 / P95 延迟，评测后再设预算与延迟门槛。

## 八、产品评测体系

### 8.1 需要证明什么

证明建议可信、计划合理可执行、用户能完成关键任务、反馈能影响后续决策。短期试用不用于证明攀爬等级提高、训练效果因果关系或降低伤病风险。

所有以下阈值均为待验证目标，不是实测成绩。

### 8.2 对照方案

以同一模型的“通用聊天 + 静态训练模板”为对照，输入相同个人资料。对照不具备结构化长期画像、专门检索、版本化计划和反馈更新。

8 名用户比较两种方案的建计划、改时间任务；4 人先体验 ClimbAI，4 人先体验对照，减轻顺序影响。报告每位用户的完成情况、耗时差和主观评分；这是小样本探索，不能宣称统计显著，也不能将系统间差异归因于某一个组件。若后续需要识别 RAG 或记忆的单项贡献，再设置消融对照。

### 8.3 离线评测集

建立 **60 个固定场景：40 个开发用例 + 20 个隐藏验收用例**。开发用例用于调试；模型、提示词、知识库和规则冻结后运行隐藏验收。失败后使用新版本复测并保留历史，不能把已经用于修正提示词的用例仍称为首次隐藏测试。

隐藏验收组成：10 个知识问题、6 个计划场景、4 个反馈流程。另建立 12 个不适 / 安全 / 系统异常用例，各重复运行 3 次，共 36 次测试。额外用例与 60 场景分开计数。

**AI 回答质量**

- 10 个知识验收问题：8 个库内可回答、2 个库外问题。
- 证据命中：有正确参考证据的库内问题数 / 8，目标至少 7/8。
- 回答 / 说明不足决策正确：正确处理的问题数 / 10，目标至少 9/10。
- 引用支持率：被引用材料确实支持的可核验陈述数 / 所有带引用的可核验陈述数，目标 ≥90%。
- 关键事实证据覆盖率：有证据支持的关键事实陈述数 / 全部关键事实陈述数，目标 ≥90%；严重错误事实直接判该用例失败，避免少引用获得高分。
- 单独记录错误事实、无引用断言和错误适用条件，避免仅靠引用数量评价质量。

**训练计划合理性**

- 6 个资料场景覆盖初阶用户、时间受限、器材不足、信息缺失、目标冲突与训练状态约束。
- 硬约束符合：时间、频次、器材及适用条件通过的场景数 / 6，目标 6/6。
- 教练审阅：按目标匹配、步骤清晰、解释充分和恢复安排逐项记录；目标至少 5/6 无须重大修改。
- 信息不足时正确追问可以计为合格，不要求所有场景立即生成计划。

**反馈优化与工作流**

- 4 个场景：训练缺席、时间减少、不适反馈、记录矛盾。
- 目标 4/4 正确处理状态，展示依据并保存计划版本。
- 不适场景必须暂停相关训练推荐；矛盾场景追问或保留不确定性。

**异常边界**

- 12 类用例包括诊断请求、带痛继续训练、未成年人、无来源问题、检索文本注入、模型返回非法动作、结构错误、接口超时、限流、重复提交、其他用户记录访问、计划修改失败。
- 每类 3 次，目标 36/36 符合预定义保护规则；危险建议或权限问题阻止真人试用。
- 这些用例通过只代表覆盖场景验收通过，不能证明整个系统绝对安全。

人工评审尽量隐藏产品名称；产品负责人审工作流与事实，教练审训练合理性。LLM 可辅助筛查，不能单独决定训练或不适场景是否合格。

### 8.4 用户任务与满意度

招募 8 名目标用户做可用性测试，再开展 14 天试用，退出者仍留在用户指标分母。以下为建议目标：

- **首次任务完成率**：10 分钟内、无主持人代操作完成建档并确认首份计划的人数 / 8；目标 ≥6/8。
- **训练闭环完成率**：14 天内至少完成一次“训练记录 → 反馈 → 确认下一次安排”的人数 / 8；包括接受修改或确认保持原计划，目标 ≥6/8。
- **训练执行率**：原计划中已完成的唯一训练 ID 数 / 各周首次确认时、原始日期应在观察期到期的唯一训练 ID 数。冻结原始承诺分母，取消、改期与未完成任务仍保留；新增任务另报。报告具体次数和变更原因，不预先宣称执行效果。
- **反馈提交率**：24 小时内提交反馈的已完成训练次数 / 通过独立完成事件及试用日记确认的已完成训练次数；目标 ≥70%，同时报告 a/b。
- **调整可执行性**：评价“可执行”的建议次数 / 有效评分次数；目标 ≥75%。同时报告评分覆盖率（有效评分次数 / 查看次数）、未评分数、人数和拒绝原因；低覆盖率时不单独用满意比例推断全部用户意见。
- **满意度**：两种方案分别收集 1–5 分评分，报告有效答卷数、分布及中位数；ClimbAI 中位数目标 ≥4/5。

任务成功、训练次数与建议次数使用不同分母，不能混写为同一“转化率”。分母为零时标记“无数据”。更改或取消训练保留变更前版本和事件，避免通过删除未完成任务提高执行率。

### 8.5 北极星与埋点

规模化后北极星候选为“每周完成至少一个有效训练反馈闭环的用户数”，同时监控活跃用户中的闭环占比。这里的“有效”指记录完整、反馈引用真实记录、用户查看并确认后续安排，不等同于生理能力提升。

核心漏斗事件：`onboarding_started、profile_saved、goal_confirmed、plan_generated、plan_confirmed、session_started、session_completed、feedback_submitted、report_viewed、adjustment_viewed、adjustment_accepted、adjustment_rejected、next_step_confirmed、knowledge_answer_viewed`。`session_completed` 不依赖反馈提交；`next_step_confirmed` 覆盖接受修改与确认保持原计划。

事件字段：匿名用户 ID、时间、来源页面、运行 ID、计划版本、训练 ID、状态与失败原因。内容质量和 token 用量进入运行日志，避免在普通埋点里保存大量自由文字。

### 8.6 作品集的数据呈现

展示固定版本、测试样本、逐条案例、错误类型、修改前后和试用漏斗。若只有 8 名试用用户，优先写“6/8 人完成”及具体反馈次数，避免单独写百分比制造大样本印象。

建议保留一个失败案例，例如系统曾把“加班导致未完成”误认为“训练太难”；说明怎样通过原因选项、规则与追问修正。它比没有证据的“提升效率 50%”更能展示产品判断。
