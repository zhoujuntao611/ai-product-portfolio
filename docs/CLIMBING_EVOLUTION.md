# 攀岩方向：ClimbAI 与攀迹怎样保留

更新于 2026-10-23。作品集以攀迹为当前主项目，ClimbAI 保留为早期 Web 探索和可体验的历史原型。

## 为什么不并列成两个主项目

两者都围绕训练记录、反馈和下一步行动，面向的攀岩爱好者也有重叠。如果分别用“AI 攀岩助手”介绍，读者容易看到两套相近功能，却看不到选择如何发生。

值得展示的是关注点的变化：先探索建议怎样生成和确认，再聚焦训练事实怎样方便地留下、视频怎样找回、下次怎样继续。这个变化体现产品范围的调整，尚不能证明新方向已获得市场或用户效果验证。

## ClimbAI 保留什么

早期问题是“在目标、时间与器材约束下，下次怎样安排训练”。保留画像、知识引用、计划版本和用户确认流程，以及对应的产品文档和后端实验。

- 在线 Web 演示已撤下，原地址跳转到攀迹。
- [源码与运行方式](../projects/climbai/README.md)保留，支持复现历史实现。
- [模型实验](LIVE_PRACTICE_20261019.md)保留：时间条件变化后，生成调整并经用户确认。该记录有未完全覆盖的知识问题，不能包装成所有任务均成功。
- 保留构建、回归和必要的兼容性修复。新增攀岩产品功能优先在攀迹评估，不再维护两份并行功能路线。

这里的“早期探索”是作品集与维护定位，不是将整个 GitHub 仓库归档，也不删除可运行演示。

## 攀迹承担什么

当前问题是“在岩馆里把一次训练记下来，之后找回同一线路的尝试和视频”。[攀迹](../projects/panji/README.md)重点保留选馆、连续记录、草稿、线路项目、视频回看、文字复盘和目标核对。

AI 只在记录之后参与文字复盘。程序提供统计事实，建议经用户确认或修改；没有移植 ClimbAI 的知识库、画像或周计划，也没有视频动作识别。

后续优先验证首次记录、连续记录时的打断、找回历史视频和下次目标核对。先观察实际使用，再决定是否引入规划、检索或更多模型能力。

## 产品演进与代码关系分开说明

- ClimbAI：React／FastAPI，浏览器演示与后端分别持久化，支持知识检索与规划实验。
- 攀迹：微信原生小程序／云函数，支持训练记录与文字复盘，本机视频与云端记录按产品约定分开保存。
- 两者是同一问题方向上的独立实现；没有证据表明旧后端或模块已移植，因此不称“ClimbAI 已迁移为攀迹”。
- 两套记录和账号不互通，没有自动导入、同步或合并；不为整理作品集移动数据库或用户文件。
- [2026-10-15 小程序迁移建议](../projects/climbai/docs/MINIPROGRAM.md)保留为历史方案。它讨论的 Taro／FastAPI 路径并非攀迹的实际实现路线。
