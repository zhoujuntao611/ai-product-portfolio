主要功能

训练记录

按日期查看每次到馆训练，连续记录多次尝试。

线路历史

将不同日期的尝试关联到同一条线路，保留卡点和完成情况。

视频回看

在尝试记录里播放视频，进入视频工具慢放、标记时间点或对照两段视频。

为什么这样做

视频放在对应的尝试里

视频放在对应的尝试记录里，回看时就知道当时卡在哪里。哪些尝试属于同一条线路，由用户自己选择，避免同名线路混在一起。

视频入口为什么放在尝试记录里

回看视频时，用户需要同时知道是哪次尝试、卡在哪里。因此把播放入口放回对应记录，慢放和对照留在视频工具中。

同一条线路由用户关联

不同岩馆可能有同名线路，岩馆也会换线。用户明确选择关联对象，可以减少历史记录混在一起的情况。

训练总结怎么生成

次数和完成率由程序计算。模型根据文字摘要提供训练建议，用户确认后保存；视频不发送给模型，也不提供视频动作分析。

当前为 0.2.2 开发预览，记录、线路关联和视频回看流程已实现。完整手机验收及小程序公开发布仍待完成。

维护者凭什么相信补丁修好了问题？

重复答疑占用时间，群聊反馈又容易缺少环境和复现步骤。即使 AI 给出代码，维护者仍要重新整理问题、检查补丁、确认测试。Oriel 把问题、补丁和测试记录整理在一起，方便维护者检查。

01

成员留在熟悉的群聊里

直接提问或描述问题。有效反馈由维护者通过 /issue 沉淀到固定 Gitee 仓库，关联原始消息，重复提交按来源去重。

02

修复任务有固定起点

维护者使用 /fix 触发任务，重新读取 Issue，锁定 Base Revision 和验收命令；同一 Issue 正在处理时，不重复启动修复。

03

进度与结果回到原问题

进度会回复到原来的飞书消息或话题。通过验证后提供候选补丁；失败或受阻时说明原因。

在干净目录里重新应用补丁，再跑一遍测试。

两个独立工作目录

Repair Worktree 负责修改。Verifier Worktree 从干净版本重新应用 Patch，再跑固定验收命令，减少修复环境残留对结果的影响。

一份可审查的候选包

交付 CANDIDATE.md 与 candidate.patch，说明变更文件、基准版本、命令退出码和测试日志，方便维护者逐项核对。

明确的任务终态

candidate_ready 表示候选可供审查；verification_failed 表示验收未通过；blocked 说明当前阻碍。

当前交付物是本地 PR Candidate。实际创建远程 PR、代码审查与合入由维护者完成；候选通过验收，也需要结合测试覆盖范围判断。

几次实验的结果

测试通过后仍需人工审查

固定验收只覆盖已知条件。Agent 交付补丁和测试记录后，仍由维护者结合问题上下文审查，再决定是否创建 PR 与合入。

Schema Token 少了 92.89%，为什么仍未得到正向结论？

PicoBench 固定任务、模型、预算和 Verifier。项目的 Tool Disclosure 实验记录中，Schema Token 减少 92.89%，但通过数从 24 降到 23，延迟也上升，因此不认定为正向优化。成本需要结合验收成功数一起看。

这项结果有项目内部实验记录，公开源码尚未附原始运行凭证，本次未重新运行。查看指标与证据范围 ↗

48 个任务通过数从 15 到 24，为什么 Skill 仍要人工激活？

Runtime 侧的经验复用实验用版本管理、相关性选择、独立验证与失败回退约束候选 Skill。项目记录中的受控 A/B 覆盖 6 类能力、48 个未见及干扰任务，通过数由 15/48 提升至 24/48，增加 18.75 个百分点；该集合中没有原本成功的任务在加入经验后失败。

混淆型负例仍有误选，因此候选保留人工确认。这是固定任务集合上的实验结果，原始凭证尚未公开，尚不能据此推断真实社区的修复成功率。把维护者 Candidate 进一步提炼为 Skill，仍属于后续接入计划。

成本下降 72.08%，具体和什么比较？

36 组配对、72 次 Trial、504 次真实 DeepSeek 调用中，两组均 36/36 通过。比较“稳定请求前缀”与“每次调用扰动前缀”后，单位成功任务估算成本的任务聚类配对估计下降 72.08%。对照组是实验条件，使用冻结的价格快照；这个数值不代表产品改版前后的账单节省。

成本实验设计、结果与边界 ↗

Pico Runtime 如何承接问答和后台修复？

Python asyncio 会话级 Lane 保持同会话有序，前后台使用独立并发池；Context 按预算组装，Session、长期记忆与 Skill 分开管理。工具根据读写属性安排执行，安全读取可以并行，写操作保留顺序。CLI、TUI、Gateway、定时任务和飞书共用 Turn 运行时。

真实 Agent 实验中，4,160 次 Turn 有 4,158 次通过验收（99.95%），前台 P95 观测值从 13.57 秒降至 11.66 秒。两次回复缺少验收标记，未达到预注册的全部通过门槛，报告保留 claim_eligible: false。这些是评测请求，不能作为社区用户规模或已达成的线上 SLA。

调度实验与验收记录 ↗

跨阶段出错时，怎样定位？

每个 Turn 关联统一 Trace ID，分开记录模型、工具、记忆、任务终态与投递。1,000 组确定性配对中，开启追踪的一侧实现完整链路关联；本地测试的 P95 耗时差为 2.245 毫秒，每个 Turn 约写入 25.1 KiB。这是小规模本地基线的绝对开销估计，不能外推为线上开销比例。

02

03

主要功能

回复与资料一起看

保留审核记录

保存草稿修改、问题标记和处理结果，也可以导出审核记录。

为什么这样做

让客服核对后再使用

政策资料可能缺失，客户问题也有特殊情况。先整理草稿与引用，再由客服核对、修改并决定处理方式。

为什么保留人工审核

资料可能缺失，客户问题也可能包含特殊情况。工具负责整理草稿和引用，审核者核对后决定如何使用；系统不自动向客户发送消息。

一次条款检查的修改

测试中，客户问退款到账时间，草稿却引用了“付款后 7 天内申请退款”。后来将申请期限与到账时间分开检查，没有对应资料时提示补充或转人工。

这轮 26 项回归说明了什么

本轮固定 26 项合成开发回归，从冻结 v2.0 的 14/26 通过增至 v2.1 的 26/26；原先失败的 12 项在同题复测中通过。

这套回归真实模型调用为 0 次，两个模型相关用例使用模拟响应。题目均参与修复，尚未用未参与调优的新样例验证，也不能证明模型比规则更有效。

界面预览应用截图 · 示例数据 · 点击放大分析报告导入订单检查数据分析报告导入订单检查数据使用流程主要功能设计取舍项目资料

怎么使用

01

导入订单表

上传 CSV，预览数据，确认哪一列是日期、金额和退款。

02

选择分析内容

输入常见订单问题，或选择收入、渠道、退款示例，再确认日期和计算方式。

03

查看并导出报告

查看汇总、渠道图表和明细。点击数字旁的引用可以核对计算依据。

主要功能

导入前检查数据

检查日期、金额、重复行和空值。有问题时，由用户确认处理方式。

常用订单分析

查看收入、订单数、渠道比较，以及退款金额和退款订单占比。

结果可以核对

报告保留筛选条件和原始数据行，支持导出 Markdown 和 JSON。

为什么这样做

退款按哪个日期算

按订单日和退款日统计，退款金额可能不同。查询前先确认按哪种日期算，报告里保留筛选条件和订单明细，方便核对。

退款按哪个日期统计

同一张九笔订单示例表，按订单日期统计二月退款为 30 元，按退款发生日期统计为 120 元。两种方式回答的问题不同，因此查询前让用户明确选择。

条件冲突时先确认

当问题要求按退款日期，而界面选择按订单日期，系统会暂停分析，提示调整条件。不会直接替用户选择一种计算方式。

如何检查计算结果

用可以手算的示例订单核对结果，并保留三版修改记录。同组 22 项已知输入最终全部通过；这些结果只说明已知问题得到修复，不代表任意问题都能正确回答。

项目资料

当前状态

已实现 CSV 导入、数据检查、常用订单分析和报告导出。问题由规则识别，当前没有外部模型调用。

当前处理单张订单表，不支持多币种混算或分次退款。订单收入不等于利润，也不能单凭这张表解释经营变化的原因。
