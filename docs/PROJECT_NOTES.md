从分散的反馈到可执行的维护任务

群聊反馈容易缺少环境和复现步骤。即使 AI 给出代码，开源维护者仍要补齐问题、检查改动、确认测试。Oriel 把原始反馈、补丁和测试记录放在同一流程中，方便逐项审查。

我的工作：定义从反馈整理到修复验收的产品流程，设计实现 Pico Runtime 与 PicoBench，并通过固定任务与失败路径检查方案。开发过程中结合 AI 编程工具完成实现与迭代。

01

成员留在熟悉的群聊里

直接提问或描述问题。有效反馈由维护者通过 /issue 沉淀到固定 Gitee 仓库，关联原始消息，重复提交按来源去重。

02

修复任务有固定起点

维护者使用 /fix 触发任务，重新读取 Issue，锁定 Base Revision 和验收命令；同一 Issue 正在处理时，不重复启动修复。

03

进度与结果回到原问题

进度会回复到原来的飞书消息或话题。通过验证后提供候选补丁；失败或受阻时说明原因。

三个决定，控制任务从哪里开始、到哪里结束

维护者确认后再启动任务

普通成员可以反馈问题，创建 Issue 与修复由维护者明确触发。保留确认步骤，关联原消息并去重，避免把未核实的群聊直接变成仓库任务。

补丁离开修复环境后再验一次

修复目录中的测试通过后，从同一基准版本创建干净验证目录，重新应用补丁并运行固定命令，检查结果是否依赖修复时遗留的文件与状态。

让维护者拿到可审查的依据

通过时交付 CANDIDATE.md、补丁、变更文件、退出码与日志；失败或受阻则交付诊断。维护者可以检查改动与验收范围，再决定是否采纳。

两组实验，检验成本与任务完成

先固定任务与验收条件，再比较成本和调度表现。以下实验公开了方法、结果摘要与复核命令；原始付费运行凭证尚未公开。

在任务通过的条件下比较调用成本

72 次 Trial、504 次真实 DeepSeek 调用，两组均 36/36 通过。12 个固定用例各重复 3 次，对比稳定请求前缀与逐次扰动前缀，覆盖对话、长历史与工具链。

单位成功任务估算成本的任务聚类配对估计下降 72.08%。结果来自冻结负载下的前缀对照；费用按冻结价格估算，尚未与实际账单核对。

响应更快，还要检查任务是否完成

4,160 次真实 Agent Turn，4,158 次满足任务验收。80 组配对比较全局 FIFO 与会话 Lane，前台 P95 观测值为 13.57 秒 → 11.66 秒；负载是专门构造的队头阻塞场景。

两次回复正常结束但缺少任务专属标记，未达到预注册的全通过标准。因此保留延迟观测值，不认定整体优化通过。

Schema Token：减少输入后，为什么没有采用？

PicoBench 固定任务、模型、预算和 Verifier。Tool Disclosure 内部实验中，Schema Token 减少 92.89%，通过数却从 24 降到 23，延迟也上升。因此不认定为正向优化，成本要结合验收成功数一起判断。

Skill 受控实验：48 个任务与人工激活

Runtime 侧的经验复用实验以版本管理、相关性选择、独立验证和失败回退约束候选 Skill。受控 A/B 覆盖 6 类能力、48 个未见及干扰任务，通过数由 15/48 到 24/48；该集合中没有原本成功的任务在加入经验后失败。

混淆型负例仍会误选，因此保留人工激活。结果来自固定任务集，原始凭证尚未公开；维护者 Candidate 到 Skill 的接入仍待完成。

Runtime 架构：会话、上下文与工具执行

Python asyncio 会话级 Lane 保持同会话有序，前后台使用独立并发池；Context 按预算组装，Session、长期记忆与 Skill 分开管理。工具根据读写属性安排执行，安全读取可以并行，写操作保留顺序。CLI、TUI、Gateway、定时任务和飞书共用 Turn 运行时。

追踪：定位跨阶段错误的成本

每个 Turn 关联统一 Trace ID，分别记录模型、工具、记忆、任务终态与投递。1,000 组确定性配对中，开启追踪的一侧实现完整链路关联；本地 P95 耗时差为 2.245 毫秒，每个 Turn 约写入 25.1 KiB。测量基于短时本地任务，不外推线上相对开销。

为什么这样做

有引用，还要核对它是否回答了问题

“付款后 7 天内申请退款”不能回答“多久能到账”。因此，我将申请期限与到账时间分开检查；缺少对应资料时，系统先提示补充信息或转人工，再由客服审核。

验证结果

以下为两批独立实验：一组用于固定合成开发回归，另一组验证历史模型接入与已知场景处理，样本与测试目的不同。

26 项合成开发回归：14/26 → 26/26。冻结 v2.0 与修复后 v2.1 使用同一组输入，原先失败的 12 项同题复测通过。题目均参与修复，尚未用未参与调优的新样例验证；该套件没有真实模型调用，两个模型相关用例使用模拟响应。

历史真实模型接入：16/24 → 24/24。2026-10-19 在固定构造场景中接入 DeepSeek，经同题修复后复测；修复后的规则流程也为 24/24。这组结果用于验证接入与已知场景处理，不作为模型相对规则的增益。

为什么保留人工审核

资料可能缺失，客户问题也可能包含特殊情况。工具负责整理草稿和引用，审核者核对后决定如何使用；系统不自动向客户发送消息。

历史模型调用与对照设置

历史实验共记录 44 次成功模型调用：修复前产品流程 7 次、修复后 13 次、同模型直接判定对照 24 次。部分任务由规则直接分流，场景数与调用数分别记录。

运营要核对什么，我设计了什么

面向需要核对收入、渠道与退款的运营，我设计 CSV 接入、字段匹配、质量检查、统计口径与报告导出流程，采用 AI 编程协作实现。首版聚焦单张订单表的收入、渠道与退款分析，让每项结果都能追溯到筛选条件和原始数据行。

01

导入订单表

上传 CSV，预览数据，确认哪一列是日期、金额和退款。

02

选择分析内容

03

查看并导出报告

查看汇总、渠道图表和明细。点击数字旁的引用可以核对计算依据。

主要功能

导入前检查数据

检查日期、金额、重复行和空值。有问题时，由用户确认处理方式。

常用订单分析

查看收入、订单数、渠道比较，以及退款金额和退款订单占比。

结果可以核对

报告保留筛选条件和原始数据行，支持导出 Markdown 和 JSON。

为什么这样做

系统不能替用户决定退款归在哪个月

同一张九笔订单示例表，二月退款按订单日算为 30 元，按退款发生日算为 120 元。两种口径回答不同问题；当提问与界面选择冲突时，我选择暂停查询、先确认条件，报告再保留原始行号与计算依据。

条件冲突时先确认

当问题要求按退款日期，而界面选择按订单日期，系统会暂停分析，提示调整条件。不会直接替用户选择一种计算方式。

如何检查计算结果

用可以手算的示例订单核对结果，并保留三版修改记录。同组 22 项已知输入测试全部通过，结果用于验证固定测试集中的计算与流程回归。

视频放在对应的尝试里

为控制存储成本，训练记录支持云端保存，视频及关联信息保留在当前设备。因此视频不跨设备同步；换机或清理微信数据前，应保留相册原片。
