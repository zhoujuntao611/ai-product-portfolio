2026-10-19，使用 DeepSeek-V4-Pro 实际运行客服证据选择、训练计划生成、反馈归纳与知识问答。项目验证记录共保存 **47 次成功 API 调用**，包括同模型对照；另对订单 CSV 分析重新执行验收。

## SupportFlow 从可运行到能处理自然表达

首轮将 24 个新编业务场景冻结后，比较规则流程、真实模型接入流程和同模型直接判定。问题覆盖正常答复、复合问句、地区冲突、资料缺失、越权请求和人工接管。

- 模型接入流程：**16/24 → 24/24**。
- 规则流程：18/24 → 24/24。
- 同模型直接判定：23/24；提供相同政策内容、元数据、客户地区与快照日期。
- 原有固定验收：31/31，扩展回归 60/60；当前工程检查 123 项通过。

### 定位到的产品问题与修复

**一句话被拆成几个失去关联的问题。** “CSV 下载链接过期了，怎样重新取得数据？”后半句丢失导出主题；“HTTP 429，按什么方式等待并重试？”又把重试误归到 Webhook。资料本来足够，却要求用户继续补充信息。

修改逗号拆分策略：将同主题背景与省略主语的追问关联，保留独立问题边界；继续逐问题检查未知能力、到账时效与高影响操作。

**引用支持检查把同义表达当成缺证据。** 客户问“发票抬头填错了”，模型选中政策“资料错误时需要更正后重新提交”，原检查要求出现“抬头”原词而阻断。修复资料更正场景的对应关系，同时保留来源与适用性校验。

**接口配置影响真实交付。** 现有配置中的模型显示名在兼容接口被拒绝，改用接口认可的 `deepseek-v4-pro`。证据选择任务关闭不必要的长推理，增加请求 ID、用量记录与可配置超时。

### 调用与资源记录

首轮产品流程调用 7 次模型，修复后调用 13 次；其余场景由明确的业务规则直接分流。同模型对照调用 24 次，共 44 次成功调用。累计输入 58,825 tokens、输出 666 tokens。修复后 13 次模型场景的完整流程耗时中位数约 10.16 秒。

本轮规则修复后也达到 24/24，因此这组结果体现的是上下文与校验策略的改进，不能解读为模型相对规则的增益。此处通过数统计预先定义的任务处理和证据要求；问题为人工构造，修复后的同题复测属于回归。原始输出、请求 ID 和逐题判分保留在报告中。

### 评分复核

原问题文本始终未变。首轮结果审阅后修正两条等价判定：地区矛盾返回 `conflict` 或 `needs_context` 均视为正确澄清；企业合同问题直接引用“以合同为准”条款也可正确回答。统一复核后，同模型对照由初始评分 21/24 改为 23/24，产品首轮仍为 16/24。原评分、原输入和重评分文件均保留。

## ClimbAI 真实模型参与训练与反馈决策

通过应用 API 跑通建档、生成、确认、记录、反馈与调整：

1. 用户条件为每周两次、每次最多 45 分钟、关注脚点观察与记录。
2. 模型从库内练习生成两次安排，分别为 **35 分钟和 30 分钟**，通过时长、器材与练习 ID 校验。
3. 记录实际训练 25 分钟，并反馈临时加班导致时间不足。
4. 模型归纳主要原因是时间限制，流程将下一次安排从 **30 分钟缩短为 25 分钟**。
5. 用户确认后生成新计划版本；原计划与修改依据可回看。

真实调用 3 次，分别用于计划生成、反馈归纳和知识回答；累计输入 2,384 tokens、输出 377 tokens。九项流程检查中八项达到初始预设：一条复合知识问题只检索到记录字段资料，模型返回记录建议并标注资料不足，尚未完整覆盖“怎样调整下次安排”。这一结果与原始响应一起保留。后端现有 116 项测试通过。

增加 `chat_json` 接入模式，将 JSON Schema 放入任务要求以适配提供 JSON object 输出的服务；业务层继续检查练习、时长、器材、引用和用户确认。调用记录只保存请求 ID、模型、耗时与用量，不保存密钥、请求头或模型内部推理。
